### 2.2 Retention decision

**Decision: no cleanup is performed on tracked checkpoints, and the storage
constraint is recorded rather than converted into a deletion.**

The reasoning:

1. The checkpoints are **git-tracked**, so they are repository content, not
   runtime garbage. Removing them would be a source change to the repository's
   committed state, and the directive forbids doing so to create space.
2. Their aggregate size is **~3 MB**. They are not the cause of the storage
   pressure and are not worth a retention mechanism.
3. They are **chained** through `previous_checkpoint_id`, and `load_checkpoints/2`
   reconstructs state from the layer directory. A bounded retention policy would
   have to preserve the chain ancestors of the newest checkpoint and the
   recovery index — a correctness question, not a housekeeping one.
4. The unbounded growth that *does* matter is the runtime's **per-event** files
   under `events/`, and the untracked checkpoints a test run creates beside the
   tracked ones. Removing untracked generated files is safe: they are runtime
   artefacts with no recovery dependency, because the tracked checkpoint for the
   same layer remains.

**What was done.** The untracked runtime artefacts generated by earlier test
runs were removed (944 files at TCP-002.5; none remain). **No tracked file was
deleted, moved or rewritten.** No retention mechanism was implemented, because
implementing one correctly requires the chain-recovery analysis above, which is
larger than this checkpoint's scope and is registered as an open item.

**Operational note for the next checkpoint.** The runtime writes one file per
event and one per checkpoint with no bound, into a **git-tracked** directory
with no `.gitignore` rule. That is the actual unbounded-growth mechanism and it
should be addressed by moving runtime-generated state to an ignored location —
but only after every reader and recovery path has been verified, which is
exactly the kind of change that must not be made blind.

## 4. Stages 2–5 — What was implemented

### 4.1 `Outcome` extended (Stage 2)

The existing struct was extended, not replaced. It now carries:

* **binding** — `forecast_digest`, `outcome_definition_digest`, `horizon_digest`;
* **observation identity** — `observation_id`, `source_identity`, `source_type`,
  `source_record_id`;
* **evidence** — `evidence_ref`, `evidence_digest`, `evidence_schema_version`;
* **distinct timestamps** — `event_at`, `published_at`, `acquired_at`,
  `verified_at`, alongside the legacy `observed_at`;
* **verification** — `verification_status`, `verification_policy_version`,
  `assurance`.

`bound?/1` and `eligible_for_resolution?/1` make the legacy boundary explicit:
an outcome with no binding and no evidence is `legacy_unverified`, is **not
bound**, and is **not eligible**. A bound outcome that has not been verified is
a *different* condition — it is waiting for the verifier — and it is reported
as such. A missing source timestamp stays missing; it is never filled with the
retrieval time.

`Outcome.content_digest/1` is the canonical digest of an observation's
*content*: the forecast it belongs to, what was observed, when the event
happened, when the source published it, when it was acquired, and which
evidence it rests on. The verification state is deliberately excluded, because
it is applied *to* the observation rather than being part of it.

### 4.2 `Observation` — the binding (Stage 3)

`Tiannara.Forecasting.Observation.bind/2` retrieves the forecast from the
**canonical registry** and derives the forecast digest, outcome-definition digest
and horizon digest from that **registered record** — not from the caller's copy
of the forecast. The caller cannot supply them. A forecast that shares an id
but carries a different horizon, version or outcome definition is refused with
`:forecast_does_not_match_registered` rather than quietly bound.

It refuses with exact reasons: `:forecast_not_registered`,
`:forecast_does_not_match_registered`, `:evidence_reference_missing`,
`:evidence_digest_missing`, `:source_identity_missing`,
`:forecast_registry_unavailable`.

It also refuses `:verification_status_not_acceptable_at_binding`: an
observation is bound **before** it is verified, so an adapter that arrives with
a verification status has skipped the verifier and is turned away rather than
silently downgraded.

### 4.3 `OutcomeVerifier` — independent inspection (Stage 4)

The verifier is given the registered forecast, the bound observation and an
**evidence reader**. It:

1. retrieves the immutable evidence itself;
2. **re-digests the raw bytes** and compares them with the recorded digest;
3. parses the evidence with a trusted parser and compares it with the
   forecast's declared outcome space — it never trusts the adapter's parsed
   `observed_outcome`;
4. applies the registered typed horizon and the publication policy;
5. verifies source identity;
6. reports the assurance **dimension by dimension**.

**A completed verification always returns `{:ok, result}` — including a
negative verdict.** A negative verdict is a finding, not an absence of
findings. The statuses are distinct and are not collapsed:

| Status | Raised when |
|---|---|
| `:verified_with_limited_source_assurance` | integrity, source identity, semantics and temporal eligibility all established, but publisher authenticity was not |
| `:requires_review` | the outcome definition is missing, or the evidence is ambiguous |
| `:rejected` | the digest does not match, the evidence does not parse, the value is outside the declared outcome space, or the event/publication falls outside the horizon |
| `:unverified` | a required check could not be completed — the event timestamp or the source identity is missing |
| `:unavailable` | the evidence or its store could not be reached |
| `:verified` | **unreachable**: no publisher signature is verified, so the strongest status the implementation can produce is the limited one |

`OutcomeVerifier.apply/2` is the **only** sanctioned verification transition.
It refuses a result that is not bound to the observation — by observation id,
evidence digest, forecast id and forecast digest — it refuses an unsupported
policy version, and it recomputes the record's own `record_digest` so that a
tampered record is detected. It also compares the record's `observation_digest`
against the observation's current content digest, so an observation cannot be
verified and then have its observed value or timestamps changed.

### 4.4 The resolver enforces the registered horizon (Stage 5)

`OutcomeResolution.validate_link/2` now additionally checks, against the
authoritative forecast:

| Check | Failure |
|---|---|
| The observation is bound (binding + evidence present) | `:legacy_outcome_not_eligible` |
| The forecast digest matches | `:forecast_digest_mismatch` |
| The outcome-definition digest matches | `:outcome_definition_digest_mismatch` |
| The horizon digest matches | `:horizon_digest_mismatch` |

`validate_horizon/2` enforces the **forecast's own** horizon:
`:typed_horizon_missing`, `:event_timestamp_missing`, `:event_outside_horizon`,
`:publication_outside_policy`. A caller cannot substitute a horizon, because
the horizon used is the forecast's own. The horizon check runs **before** the
verification check, so a temporal violation is reported as a temporal
violation rather than being hidden behind a verdict.

`validate_verification/2` requires a verification record — not a status field
on the outcome. Without a record there is nothing that establishes the
evidence was ever inspected, and an adapter that asserted its own verification
would be believed. The record must be bound to the forecast, the observation
and the evidence; it must carry a supported policy version; its own digest must
be intact; the observation's content must be exactly what was verified; and
its status must be one the resolver accepts. Failures are exact:
`:verification_record_missing`, `:verification_policy_unsupported`,
`:verification_record_tampered`, `:verification_forecast_mismatch`,
`:verification_forecast_digest_mismatch`, `:verification_observation_mismatch`,
`:verification_evidence_mismatch`, `:observation_content_tampered`,
`:verification_not_sufficient`, `:verification_status_mismatch`.

The resolution result now preserves the full provenance: forecast digest,
outcome-definition digest, horizon digest, observation id, evidence digest,
the four timestamps, the verification status, the verification policy version
and the verification record's digest.

### 4.5 Live verification vs. historical recovery

The HMAC is a **live-process tamper check**, not a durable credential: every
restart generates a new key, so a previously signed record fails the HMAC
check against the replacement key. That failure is not by itself evidence of
tampering — it may be a historical record from a restarted authority.

The resolver distinguishes the two cases explicitly:

1. **Live verification** — the HMAC passes. Re-execution against the
   immutable evidence is performed as defence in depth when a reader is
   supplied, but is not required.
2. **Historical recovery** — the HMAC fails. Re-execution is **required**,
   and the recomputed result must agree with the persisted record on
   **status, reason and the complete assurance map**. Only then is the
   resolution permitted.

Authentication is never skipped: a record that fails both the HMAC and
re-execution is refused. The two paths are separate code paths, not a single
"skip the check" branch.

### 5.1 The limitation that is not hidden

A verification record is **integrity-bound, not authenticated**. Its
`record_digest` detects modification; it does not prove that the verifier
process produced it. This is the same standing limitation as the durable log's
chain (TCP-B-058, TCP-B-061). The reproduction path is to re-run `verify/3`
against the evidence store. The implementation does not claim otherwise.

## 8. Stage 12 — Lifecycle and assurance observability

`Tiannara.Forecasting.Lifecycle` is a supervised, process-scoped ledger that
answers one question: **where has the lifecycle actually reached, and what has
actually been established?** It is wired into the real paths — `Outcome.new/3`,
`Observation.bind/2`, `OutcomeVerifier.verify/3` and
`OutcomeResolution.resolve/4` — so it reports what happened rather than what
was declared.

The rules it follows:

* It never reports `operational`, `healthy` or a zero failure count as a
  default.
* It never collapses materially different conditions. "No observation",
  "acquired but unverified", "verified with limited assurance", "requires
  review", "rejected" and "resolved" are separate counts.
* It never reports a state that was not reached. `lifecycle_state` and
  `transitions_proven` are derived from what actually occurred.
* When the ledger itself is unavailable it reports `available: false` and
  **presents no counts at all**, rather than presenting zeros that would read
  as "nothing happened".
* It never claims durability. The snapshot says `durable: false`,
  `scope: :process_scoped`, and names `TCP-B-064` as the reason.

It is **instrumentation, not a gate**: a ledger that is down must not stop a
forecast from being registered, bound, verified or resolved, so a recording
failure is never propagated into the business path.
