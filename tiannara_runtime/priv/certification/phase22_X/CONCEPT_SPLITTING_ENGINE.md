# Concept Splitting Engine

## Purpose

Govern the splitting of ontology concepts when multiple meanings emerge, domains diverge, evidence separates, or engineering usage diverges — each descendant preserving its parent lineage.

## Split Triggers

### Multiple Meanings
- Concept has acquired multiple distinct meanings
- Ambiguity causes confusion
- Precision requires separation

### Domain Divergence
- Concept used differently across domains
- Domain-specific refinements conflict
- Cross-domain communication breaks down

### Evidence Separation
- Evidence supports different aspects
- Different evidence sets for different contexts
- Evidential basis diverges

### Engineering Usage Divergence
- Engineering systems need distinct concepts
- Practical usage separates
- Engineering communities diverge

## Split Process

1. **Divergence Assessment**: Evaluate meaning, domain, evidence, and engineering divergence
2. **Split Design**: Design split into multiple specialized concepts
3. **Evidence Distribution**: Partition evidence across new concepts
4. **Relationship Distribution**: Distribute relationships appropriately
5. **Definition Refinement**: Refine definitions for each descendant
6. **Validation**: Validate each descendant concept
7. **Constitutional Review**: Governance approval
8. **Recording**: Split recorded with complete lineage

## Split Structure

Each split record contains:

- **Split ID**: Content-addressed identifier
- **Parent Concept**: Concept being split
- **Descendant Concepts**: Resulting concepts
- **Split Basis**: Rationale for splitting
- **Evidence Distribution**: How evidence was partitioned
- **Relationship Distribution**: How relationships were distributed
- **Definition Refinement**: Refined definitions
- **Validation Results**: Validation of descendants
- **Fingerprint**: Deterministic content hash

## Constraints

- Each descendant preserves its parent lineage
- Split records become constitutional artifacts
- All splits are replayable
