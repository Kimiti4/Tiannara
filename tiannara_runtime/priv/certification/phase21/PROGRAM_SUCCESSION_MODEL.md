# Program Succession Model (Phase 21.1)

## Purpose

Define deterministic program succession. Programs may evolve into successor programs — every successor inherits archaeological lineage while remaining a distinct constitutional entity.

## Succession Types

| Type | Description | When Used |
|------|-------------|-----------|
| Natural completion | Program achieved objectives → successor addresses remaining questions | Objectives met |
| Scope expansion | Program scope broadens → successor covers expanded domain | New questions emerge |
| Scope narrowing | Program scope narrows → successor focuses on specific findings | Findings warrant focus |
| Branching | Single program splits into multiple successors | Multiple independent directions |
| Merger | Multiple programs merge into single successor | Convergent findings |
| Replacement | Program replaced by fundamentally different approach | Paradigm shift |

## Succession Requirements

Each succession must:
1. Preserve all predecessor knowledge
2. Transfer remaining capital to successor
3. Document succession reason
4. Maintain archaeological lineage
5. Record as distinct constitutional entity
6. Preserve predecessor replay chain

## Archaeological Lineage

The succession chain forms an archaeological lineage:
```
Program A (Generation 1–100)
    ↓
Program B (Generation 101–250)
    ↓
Program C (Generation 251–500)
```

Each successor:
- Inherits predecessor's archaeology root
- Adds its own archaeology
- Both lineages remain independently reconstructible
- The full chain is traceable from any node

## Succession Record

Each succession is recorded in `PROGRAM_SUCCESSION_SCHEMA.json`:
- Predecessor and successor IDs
- Succession reason
- Inherited knowledge artifacts
- Inherited capital
- Inherited archaeology root
- New scope description
- Archaeological lineage hash
